1. ARCHITECTURAL OVERVIEW & SECURITY MODEL
================================================================================

BiteBuddy 2.0 utilizes a stateless JWT session architecture combined with
secure HTTP-only cookie transport, Next.js Edge Middleware route guards, and
strict server-side live database authorization checks.

Core Security Principles:
- Passwords are never stored in plaintext. They are salted and hashed using bcryptjs (10 salt rounds).
- Session tokens are signed using HMAC-SHA256 (HS256) via the Edge-compatible 'jose' library.
- Session cookies are strictly HTTP-only, preventing client-side JavaScript access (XSS defense).
- Cross-Site Request Forgery (CSRF) mitigation via SameSite=Lax cookie attribute.
- Live database role verification on every privileged action to prevent privilege escalation via stale tokens.
- Strict multi-tenancy: Every user membership, order, meal, payment, and audit entry is strictly scoped by 'office_id'.
- Strict Admin Quota: Maximum 2 administrators per office enforced transactionally with concurrency mutex locks.
- Last-Admin Protection: An office can never demote its last active administrator.
- Edge Route Protection: Unauthenticated and unauthorized requests are intercepted before UI rendering.

2. ROOT CAUSE ANALYSIS OF AUTH/ROUTING BUG & THE ARCHITECTURAL FIX
================================================================================

A. What Specifically Caused the Login/Signup Problem?
--------------------------------------------------------------------------------
1. Client-Side Response Property Mismatch in LoginPage:
   - The backend API (POST /api/auth/login) returned:
     { success: true, user: { role: 'ADMIN', officeId: '...', ... } }
   - The frontend login page (app/login/page.tsx) checked:
     if (data.membership?.role === 'ADMIN') { router.push('/admin'); } else { router.push('/app'); }
   - Because data.membership was undefined in the JSON response, the expression
     data.membership?.role === 'ADMIN' ALWAYS evaluated to FALSE for every login.
   - Result: Admins logging in were unconditionally pushed to '/app' (Employee Dashboard)
     instead of '/admin'.

2. Missing Next.js Edge Middleware:
   - The application previously had no middleware.ts.
   - Route protection relied exclusively on client-side React useEffect hooks.
   - Result: Direct URL navigation (e.g. typing /admin or /app) caused authentication
     flicker, partial page renders, and blank states when data APIs returned 401.

3. Inconsistent API Route Authorization:
   - Several admin API routes checked raw JWT tokens (session.role !== 'ADMIN') rather than
     verifying the live database membership via requireAdmin().
   - Result: If an admin was demoted in the database, their existing token could still call
     some administrative routes until expiration.

B. How the Architecture Was Fixed:
--------------------------------------------------------------------------------
1. Created middleware.ts running at the Edge:
   - Intercepts all requests to /admin/*, /app/*, /login, /signup, and /.
   - Cryptographically verifies session token with jose.
   - Unauthenticated visitors on /admin or /app are redirected immediately to /login.
   - Non-admin authenticated users on /admin/* are redirected safely to /app.
   - Authenticated users on /login, /signup, or / are routed to their designated dashboard.
2. Standardized API Response Contracts:
   - /api/auth/login, /api/auth/signup, /api/offices/join, and /api/auth/me now consistently
     return explicit 'role', 'redirectUrl', 'user', 'membership', and 'office'.
3. Unified Server Authorization via requireAdmin() and getCurrentUser():
   - Every administrative API route now executes 'await requireAdmin()' which queries the live
     memberships table in the database to verify active ADMIN status.
4. Protected Client Layout Shells:
   - Added auth guards to app/app/layout.tsx and app/admin/layout.tsx with sleek loading
     indicators to eliminate layout flicker during authentication resolution.

3. CRYPTOGRAPHY & TOKEN ENGINE
================================================================================

Source File: lib/auth/session.ts

A. Password Hashing:
   - Algorithm: bcryptjs with 10 salt rounds.
   - Functions:
     * hashPassword(password: string): Promise<string>
       Generates a cryptographically secure salt and returns the bcrypt hash.
     * verifyPassword(password: string, hash: string): Promise<boolean>
       Compares plaintext password against the stored bcrypt hash using constant-time
       comparison to prevent timing attacks.

B. JWT Session Signing & Verification:
   - Library: jose (Edge-compatible HMAC-SHA256).
   - Secret Key: UTF-8 encoded byte buffer from process.env.JWT_SECRET.
   - Cookie Name: 'bitebuddy_session'
   - Token Validity: 30 days.
   - Token Payload Structure (SessionPayload):
     {
       userId: string,          // Unique UUID of the user
       email: string,           // User's email address
       name: string,            // User's full name
       role: 'ADMIN' | 'USER',  // User's role within their active office
       officeId: string,        // UUID of the office workspace
       officeName: string       // Name of the office
     }

5. DATABASE SCHEMA & ENTITY RELATIONSHIPS
================================================================================

The authentication system is built on a normalized relational model:

A. USERS Table:
   - id: UUID (Primary Key)
   - name: String
   - email: String (Unique, Indexed, Case-Insensitive)
   - phone: String
   - password_hash: String (bcrypt hash)
   - photo_url: String (Optional)
   - is_active: Boolean (Default: true)
   - created_at: ISO8601 Timestamp
   - updated_at: ISO8601 Timestamp

B. OFFICES Table:
   - id: UUID (Primary Key)
   - name: String (e.g. "TechCorp Bangalore HQ")
   - admin_id: UUID (Initial Creator User ID)
   - veg_price: Number (e.g. 80)
   - non_veg_price: Number (e.g. 100)
   - cutoff_time: String (24h format, e.g. "19:00")
   - timezone: String (Default: "Asia/Kolkata")
   - week_start_day: Number (1 = Monday)
   - auto_default_enabled: Boolean (Default: true)
   - join_code: String (Unique, Indexed, e.g. "BITE-7K4P")
   - working_days: Array<Number> (e.g. [1, 2, 3, 4, 5])
   - created_at: ISO8601 Timestamp
   - updated_at: ISO8601 Timestamp

C. MEMBERSHIPS Table:
   - id: UUID (Primary Key)
   - user_id: UUID (Foreign Key -> Users.id)
   - office_id: UUID (Foreign Key -> Offices.id)
   - role: 'ADMIN' | 'USER' (Strictly typed enum)
   - default_preference: 'flexible' | 'always-veg' | 'always-non-veg'
   - is_active: Boolean (Default: true)
   - joined_at: ISO8601 Timestamp
   - updated_at: ISO8601 Timestamp

D. PASSWORD_RESET_TOKENS Table:
   - token: String (6-digit random code, e.g. "492815")
   - user_id: UUID (Foreign Key -> Users.id)
   - expires_at: ISO8601 Timestamp (15 minutes lifespan)

6. ADMIN SIGNUP & WORKSPACE CREATION FLOW
================================================================================

Route: POST /api/auth/signup
Page:  /signup

Step-by-Step Execution:
1. Client submits: { name, email, phone, password, officeName, defaultPreference, role: 'ADMIN' }.
2. Zod Validator (SignupSchema) checks all field constraints.
3. Duplicate Check:
   - Queries Users table by lowercase email.
   - If found -> Aborts with HTTP 400: "This email is already registered. Please log in."
4. User Generation:
   - Generates unique userId (crypto.randomUUID()).
   - Hashes password using bcrypt.
   - Saves User record with is_active = true.
5. Office Generation:
   - Generates unique officeId.
   - Generates unique join code (e.g. "BITE-8F2A") via OfficeService.generateJoinCode('BITE').
   - Sets default office settings (₹80 Veg, ₹100 Non-Veg, 7:00 PM cutoff, Asia/Kolkata).
   - Saves Office record.
6. Membership Generation:
   - Creates Membership linking User and Office with role = 'ADMIN'.
   - Sets selected default_preference.
7. Session Issuance:
   - Signs 30-day JWT containing { userId, email, name, role: 'ADMIN', officeId, officeName }.
   - Attaches 'bitebuddy_session' cookie with HTTP-only, SameSite=Lax, Secure flags.
8. Response & Navigation:
   - Returns { success: true, role: 'ADMIN', redirectUrl: '/admin', user: {...}, membership: {...} }.
   - Client router pushes directly to /admin.

================================================================================

Golden Rule of BiteBuddy Onboarding:
- CREATE WORKSPACE = ADMIN (Office Owners & Managers creating a new office team)
- JOIN WORKPLACE = EMPLOYEE (New Employees joining an existing office via Code or QR)
- SIGN IN = EXISTING USER (Employees and Admins returning to their active accounts)

An employee joining an existing workplace is NEVER shown "Create Office Workspace"
and is NEVER asked to type the Office / Company Name.

--------------------------------------------------------------------------------
7.1. Dedicated Join Workplace Hub (/join)
--------------------------------------------------------------------------------
Route: GET /api/offices/join?code=BITE-XXXX (Validates join code & returns office preview)
       POST /api/offices/join (Submits employee profile & joins workplace)
Page:  /join

Workflow:
1. Entry:
   - Employee opens /join on mobile or desktop.
   - Chooses between "Enter Code" (keyboard) or "Scan QR Code" (in-browser camera).

2. Option A: Enter Join Code:
   - Types or pastes 8-character code (e.g. BITE-7K4P), automatically formatted.
   - Clicks "Verify Workplace Code".

3. Option B: Scan QR Code (Mobile-First Camera):
   - Uses device camera via standard navigator.mediaDevices.getUserMedia / BarcodeDetector.
   - Points at office lunch poster or admin's screen.
   - Automatically detects QR code and transitions to verification.

4. Workplace Identification & Name Locking:
   - Server validates code via GET /api/offices/join?code=...
   - Screen displays verified office banner:
     "✓ Verified Workplace: Acme Corporation · Cutoff: 7:00 PM · Role: Employee"
   - Company name is LOCKED; employee cannot edit or alter company name.

5. Employee Profile Form:
   - Employee fills: Full Name, Work Email, Phone, Password, Dietary Preference.
   - Submits form -> POST /api/offices/join.

6. Server-Side Security & Role Assignment:
   - Server strictly creates user and membership with role = 'USER'.
   - Ignores any client attempt to supply role = 'ADMIN' or arbitrary officeId.
   - Checks if user belongs to another office -> Rejects with friendly transfer notice.
   - If existing member joins same office -> Re-authenticates without duplicating.

7. Immediate Dashboard Landing:
   - Issues HTTP-only 30-day JWT session cookie.
   - Immediately redirects to Employee Dashboard (/app) without forcing another login.

7.2. Direct Invite Link & QR Deep Link (/join/[code])
--------------------------------------------------------------------------------
Route: /join/[code] (e.g. /join/BITE-7K4P)

8. LOGIN, SIGN-IN & RE-LOGIN LIFECYCLE ENGINE
================================================================================

Route: POST /api/auth/login
Page:  /login

--------------------------------------------------------------------------------
8.1. Standard Credentials Authentication & Re-Login Protocol
--------------------------------------------------------------------------------
1. Client Form Submission:
   - Form trims email (`email.trim()`) to prevent whitespace pollution from mobile autofill.
   - Password is sent exactly as typed, preserving any deliberate spaces or symbols.
   - Inputs and submit button are locked in loading state to prevent double-click race conditions.

2. Schema Validation (LoginSchema):
   - Email: String trimmed, validated as valid email format.
   - Password: Min 1 character (Aligned with all signup schemas).
   - If invalid format -> Returns HTTP 400 with "Please enter a valid email and password."

3. Server-Side Email Normalization & Lookup:
   - Email is normalized using `email.toLowerCase().trim()`.
   - Queries database user record by normalized email.
   - If user does not exist or password_hash is missing -> Returns HTTP 401: "Email or password is incorrect."
   - If user is deactivated (`is_active === false`) -> Returns HTTP 401: "This account has been deactivated. Please contact your office administrator."

4. Cryptographic Password Verification:
   - Evaluates `bcrypt.compare(password, user.password_hash)`.
   - If hash mismatch -> Returns HTTP 401: "Email or password is incorrect."
   - (Uniform 401 response prevents user enumeration attacks).

5. Workspace Membership & Role Resolution:
   - Queries Memberships table for active workplace membership:
     `memberships.find(m => m.user_id === user.id && m.is_active)`
   - If no active membership found -> Returns HTTP 403: "No active workspace membership found for this account. Please join a workspace."
   - Server strictly determines role ('ADMIN' or 'USER') from database membership.

6. Session Token Generation:
   - Signs cryptographic 30-day JWT token with payload:
     `{ userId, email, name, role, officeId, officeName }`.
   - Attaches 'bitebuddy_session' cookie with `httpOnly: true`, `sameSite: 'lax'`, `path: '/'`, `maxAge: 30 days`, and `secure: process.env.NODE_ENV === 'production'`.

7. Deterministic Role-Based Routing:
   - Returns `{ success: true, role, redirectUrl: role === 'ADMIN' ? '/admin' : '/app', user, membership, office }`.
   - Client router immediately navigates to destination dashboard.

--------------------------------------------------------------------------------
8.2. Deterministic Sign Out / Logout Protocol
--------------------------------------------------------------------------------
Route: POST /api/auth/logout

When user signs out:
1. Server invalidates cookie: sets `expires: new Date(0)`, `maxAge: 0`, `path: '/'`, `httpOnly: true`, `sameSite: 'lax'`, `secure: production`.
2. Database user record, workspace membership, meal history, and preferences remain permanently intact.
3. User can immediately re-login with the same credentials at any time.

--------------------------------------------------------------------------------
8.3. 1-Tap Instant Demo Access
--------------------------------------------------------------------------------
- "Admin Mode" -> Logs in as admin@bitebuddy.app / password -> Opens /admin
- "Employee Mode" -> Logs in as employee@bitebuddy.app / password -> Opens /app

9. UNIFIED SESSION ENGINE & SERVER-SIDE AUTHORIZATION GUARDS
================================================================================

Source File: lib/auth/session.ts

The server-side authorization layer provides unified, bulletproof guards:

A. CurrentUser Interface:
   {
     id: string;              // User UUID
     userId: string;          // Alias for backward compatibility
     email: string;           // User email
     name: string;            // User name
     phone: string;           // User phone
     role: 'ADMIN' | 'USER';  // Live verified role
     officeId: string;        // Office UUID
     officeName: string;      // Office Name
     isActive: boolean;       // User & membership active status
     defaultPreference?: 'flexible' | 'always-veg' | 'always-non-veg';
   }

B. getSession(): Promise<SessionPayload | null>
   Reads and decodes JWT cookie, verifies user exists and is active.

C. getCurrentUser(): Promise<CurrentUser | null>
   SINGLE SOURCE OF TRUTH: Reads session token, queries live database Users table
   AND live Memberships table. Returns fully resolved CurrentUser object.

D. requireAuth(): Promise<CurrentUser>
   Calls getCurrentUser(). Throws Error('UNAUTHORIZED') (HTTP 401) if invalid.

E. requireAdmin(): Promise<CurrentUser>
   Calls requireAuth(). Verifies user.role === 'ADMIN' in the live database.
   Throws Error('FORBIDDEN') (HTTP 403) if user is not an active Admin.

F. requireEmployee(): Promise<CurrentUser>
   Calls requireAuth(). Verifies valid office membership.

G. getCurrentUserProfile():
   Returns composite { user, membership, office } for profile screens.

10. ROLE-BASED ACCESS CONTROL (RBAC) & ADMIN QUOTA (MAX 2)
================================================================================

Source Files: lib/offices/office-service.ts
              app/api/admin/users/role/route.ts
              app/admin/members/page.tsx

Rules & Enforcements:
1. MAX_ADMINS_PER_OFFICE = 2
   - Enforced by OfficeService.promoteMemberToAdmin().
   - If activeAdminCount >= 2, promotion attempts are rejected with:
     "Cannot promote employee: Maximum limit of 2 administrators per office has already been reached."
2. Asynchronous Queue Concurrency Mutex:
   - Role promotions and demotions are serialized through an asynchronous promise chain
     (roleMutationLock) with .catch() error recovery to prevent race conditions.
3. Last-Admin Protection:
   - An office must have at least 1 active administrator at all times.
   - OfficeService.demoteAdminToUser() blocks demotion if activeAdminCount <= 1:
     "Cannot remove administrator: An office must have at least one active administrator."
4. Immutable Audit Trail:
   - Role modifications are recorded in the audit_logs table ('ADMIN_PROMOTED', 'ADMIN_DEMOTED').
5. Real-Time Broadcast:
   - Role updates broadcast a 'MEMBER_ROLE_CHANGED' event across the SSE event stream.

12. PASSWORD RESET & RECOVERY ENGINE
================================================================================

Routes: POST /api/auth/forgot-password
        POST /api/auth/reset-password
Pages:  /forgot-password
        /reset-password

1. Forgot Password:
   - Generates cryptographically secure 6-digit code (crypto.randomInt(100000, 999999)).
   - Sets 15-minute expiration timestamp.
   - Anti-Enumeration Protection: Always returns success message to prevent email harvesting.
2. Password Reset:
   - Validates 6-digit code and expiration.
   - Hashes new password with bcrypt (min 6 chars).
   - Deletes used token and updates user password.

16. MULTI-TENANCY & TENANT ISOLATION
================================================================================

Every authenticated session is strictly bound to an 'officeId'.
1. Database Query Isolation:
   - All meal queries, payment ledgers, finalized orders, office holidays, push subscriptions,
     and audit logs are strictly filtered by office_id = session.officeId.
   - An employee or admin from Office Alpha cannot view or modify data from Office Beta.
2. Real-Time Pub/Sub Isolation:
   - Server-Sent Events (/api/realtime/stream) scopes broadcasts strictly by officeId.
   - Price updates, cutoff extensions, and orders in Office Alpha are never sent to Office Beta.
3. Edge Protection Isolation:
   - Middleware prevents unauthenticated cross-tenant access.
